# 仓库结构设计

## 设计目标

仓库同时解决四个问题：

1. 平台可执行：策略文件可以直接复制到聚宽运行。
2. 变体清晰：同一投资逻辑的小变体集中管理，不扩散成大量独立项目。
3. 结果可复现：旧回测永远能找到当时使用的精确源码。
4. Agent 可持续维护：硬规则自动生效，详细经验按需加载。

## 三层知识结构

### `AGENTS.md`

保存必须始终遵守的硬规则，例如目录、命名、不可变回测和聚宽兼容性底线。内容应短而稳定。

### `docs/`

保存需要长期积累但不必每次全部加载的知识，例如聚宽 API 陷阱、归档字段和实验设计。

### `.agents/skills/`

保存可重复执行的工作流。skill 告诉 Agent 在创建策略、制作变体和归档回测时按什么顺序读取哪些资料、执行哪些验证。skill 不重复保存项目事实。

## 策略族与变体

策略族由核心投资假设定义，而不是由参数定义。

以下情况通常属于同一策略族：

- 持股数从 20 改为 30。
- 调仓频率从每月改为每季度。
- 增加价值陷阱过滤或组合风险覆盖层。
- 调整因子权重、行业上限或交易阈值。

以下情况通常应新建策略族：

- 从价值选股改成日内做市。
- 从 A 股基本面数据改成期货期限结构。
- 投资目标、市场和主要数据源都发生变化。

每个 `.py` 变体都应是平台可独立运行的完整文件。虽然会有少量重复，但它避免了聚宽无法导入本地模块、线上源码与本地组合方式不一致等问题。纯函数可以通过测试和机械同步保持一致；只有变体数量明显增多时，才引入生成器。

## 回测归档

`baseline.py` 和 `variants/*.py` 是当前工作源码，允许演进。每个回测目录中的 `source.py` 是运行时快照，不允许修改。

必需文件：

- `manifest.json`：机器可读元数据和指标。
- `report.md`：人可读诊断、限制和实验结论。
- `source.py`：平台实际运行源码。

推荐保留：

- `raw/equity.csv`
- `raw/trades.csv`
- `raw/positions.csv`
- `raw/log.txt`
- `assets/summary.png`

`manifest.json` 的 `source_sha256` 必须与 `source.py` 一致。验证器会检查这一点。

## 研究执行后端

与具体投资逻辑无关、但需要在外部平台运行的可复用执行代码放在 `runners/`：

```text
runners/{platform-runtime}/
  README.md
  {runtime_module}.py
  examples/
```

runner 负责日历、撮合、账本和结果导出，不成为策略事实源。平台运行模块必须可直接上传且
自包含；示例不能冒充正式策略或业绩证据。正式运行仍归档到对应策略族的 `backtests/`，并
同时保存实际策略为 `source.py`、实际 runner 为 `engine.py` 和二者 SHA-256。

## 为什么不把回测结果集中放在根目录

结果与策略族放在一起，能让代码、研究假设、变体和证据形成一个可独立阅读的单元。跨策略比较可以后续增加顶层 `studies/`，但不能代替策略目录内的原始归档。
